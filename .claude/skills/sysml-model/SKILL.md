# SysML model

`assurance/models/sysml` describes LD-SDA as a SysML v2 text model. It is a **checked copy of the work products**,
not the record and not code generation. Until the model review (OI-8), `record.toml` says `record = "work-products"`:
**the work product wins**, and the model is regenerated or edited to match it. Nothing the model produces is
verification evidence (WP-P-07 TL-26 and TL-27, TCL1, no credit). Read the folder's `README.md` before a larger change.

## Hand-written or generated?

| Files | How they change |
|---|---|
| `Requirements`, `Satisfaction`, `Verification`, `Needs` | **Generated** by `tools/gen_requirements.py` (check R1) |
| `StateRecords`, `Sequences`, `Lifecycle` | **Generated** by `tools/gen_behaviour.py` (check B1) |
| `Timing`, `Signals` | **Generated** by `tools/gen_timing_hsi.py` (check H1) |
| `LionDriverLibrary`, `Architecture`, `Mechanisms`, `Functions`, `Security`, `Integration`, `Behaviour`, `Views`, and `views/layout.toml` | **Hand-written.** Edit them to match the work product, cell by cell; check_model says where they differ |
| `generated/*` (SVGs, `explorer.html`, the reports) | Never edited by hand |

A generated file starts with `// GENERATED by …`. Never edit one: change the work product and regenerate. Which work
product feeds which file, section by section, and which check holds each hand-written file to its table, is in
[references/sources.md](references/sources.md). Example: a change to WP-S-08 §3.1 means editing the `I-n` action in
`Integration.sysml` so that `elements`, `interfaces`, `stimulus` and `purpose` are the WP-S-08 cells character for
character (M11 compares the strings exactly), and `integrates`/`exercises` still name model elements and IF-nn.

## After a work product changes: the order

Run from `assurance/models/sysml`. Each step reads what the one before it wrote.

1. **FSR and TSR tables** (WP-C-04 §5, WP-S-02 §3-§9, WP-S-06 TSR-8xx) reach the model through the trace data:
   from the repository root, `python3 assurance/trace/tools/sync_requirements.py`, then the same with `--check`.
   Safety goals come from `assurance/trace/items/goals.yaml`. SYS, CSR, needs and test cases are read directly.
2. **Generated model files:** `python3 tools/gen_requirements.py`, `python3 tools/gen_behaviour.py`,
   `python3 tools/gen_timing_hsi.py` (each without `--check` writes; run only the ones whose sources changed, or all
   three, they are cheap). A generator that raises names the cell it cannot read: fix the work product or the
   generator on purpose, never loosen it.
3. **Hand-written files:** edit them until `python3 tools/check_model.py` passes the M rules for your table.
4. **Reports:** `python3 tools/check_model.py --write` rewrites `generated/allocation-resolution.md` (M8) and
   `generated/requirements-coverage.md` (R4). Then `python3 tools/check_model.py` must print `OK: M1-M12, …`.
5. **Architecture tables:** `python3 tools/gen_tables.py` (T1). With `record = "work-products"` it only compares;
   the fix is the same cell in the work product and the model. `--write` refuses until the lead's review switches
   `record.toml` to `model` (OI-5); do not switch it yourself.
6. **Views:** `python3 tools/render_views.py`. Every SVG carries a digest of all model and layout files, so any
   model change rewrites all of them; commit them together.
7. **Explorer:** `python3 tools/explorer.py --fragment <scratchpad>/sysml-explorer.html`, then republish (below).
8. **Downstream:** the AUTOSAR description reads the model (elements, cereal services, signals S-nn, HSI-nn). From
   `assurance/models/autosar`: `python3 tools/gen_arxml.py`, then the checks below. From the repository root, run
   the figure checks that read the model or its reports, `python3 assurance/03-system/figures/fig_s01_requirements.py
   --check` and `python3 assurance/trace/tools/trace_figures.py --check` among them (full list in
   [references/sources.md](references/sources.md)).
9. **Counts in prose:** the README's baseline numbers (requirements, allocations, §5 table) and any count a work
   product states are not checked. Update them from the `check_model.py` output, and bump the version and history of
   every page you touched (WP-P-04).

## Checks: the CI sequence

The "sysml model" job in `.github/workflows/assurance.yaml` runs exactly this, from `assurance/models/sysml`:

```bash
python3 tools/gen_requirements.py --check
python3 tools/gen_behaviour.py --check
python3 tools/gen_timing_hsi.py --check
python3 tools/check_model.py            # M1-M12, N1-N3, B1-B4, H1-H6, R1-R4
python3 tools/gen_tables.py             # T1
python3 tools/render_views.py --check
python3 tools/explorer.py --check       # also fails when the published page is behind
python3 tools/test_sysml.py
tools/pilot/validate.sh <scratchpad>/sysml-pilot   # OMG pilot 0.62.0: SysML v2 conformance
```

The pilot needs JDK 21+ (`javac`), `python3 -m pip install --user --break-system-packages zstandard`, and network to
fetch the pinned kit on first run; it must end `errors=0 warnings=0`. The "autosar description" job runs, from
`assurance/models/autosar`: `python3 tools/gen_arxml.py --check`, `python3 tools/check_arxml.py` (A1-A8) and
`python3 tools/test_arxml.py` (needs `git submodule update --init opendbc_repo`).

What each rule compares is in the README §4 table and in `check_model.py`'s docstring. Read the failing line: it
names the row, the column, the model value and the work-product value.

## Writing SysML

- `tools/sysml_lite.py` reads only the subset the model uses and refuses anything else with its line number. For a
  new construct, extend the reader and add a test in `test_sysml.py`; the pilot decides whether it is valid SysML v2.
- `item`, `view`, `via`, `state`, `flow` and other SysML v2 keywords cannot be names; the pilot parse fails.
- Every element inside the item needs an integrity; a QM to ASIL connection inside the item needs `@FfiClaim` (M7).
- A new element must also go into a security zone (M10) and an integration step (M11), and may need a `[titles]`
  display name in `layout.toml`.

## Views

A view is declared in `model/Views.sysml` (what it exposes) and placed in `views/layout.toml` (where; `kind` picks
the renderer). The renderer lives in `render_arch.py`, `render_requirements.py` or `render_se.py` and draws with
`svgkit.py`. The steps to add or change one are in [references/views.md](references/views.md). Look at every view
you change, at full width and at phone width:

```bash
node .claude/skills/assurance-figure/scripts/preview.mjs <scratchpad>/png \
  assurance/models/sysml/generated/fig-sysml-v27-mechanism-coverage-per-goal.svg --width 390
```

then Read the PNGs. About a dozen pages under `assurance/03-system` and `assurance/02-concept/fsc` embed these SVGs by path; check
their alt text and counts when a view's content changes (`grep -rn fig-sysml-vNN assurance --include=*.md`).

## The explorer page

`tools/explorer.py` builds one self-contained page (views V-01 to V-07, the model tree and an inspector). It is
published as the lead's private page at `EXPLORER_URL` in `explorer.py`, currently
<https://claude.ai/artifact/K7ttKxrqZxzVPoWiXZknix>. `tools/explorer.sha256` records the fingerprint of the fragment
last published, and `explorer.py --check` fails when the model moved on without a republish. The steps and what to
do when publishing fails are in [references/explorer.md](references/explorer.md). In short: `--fragment` writes the
fingerprint **before** you publish, so if the publish does not succeed, restore `tools/explorer.sha256`
(`git checkout -- tools/explorer.sha256`), tell the user the live page is behind, and never say it was published.

## Honesty

The model, the views and the explorer are AI-drafted (Claude), I0 under WP-M-02 §3.3, and not reviewed. Do not mark
them reviewed or approved, do not take verification credit from a check, and keep the README status line saying so.
A "verified" requirement in the coverage report means a case is specified, not that it passed. When the model and a
work product disagree, do not change the work product to suit the model unless that is the task; record a real
difference as an open item (as OI-7 does for IF-05 to IF-07). Questions only the lead can decide (switching the
record to the model, replacing a hand-drawn figure, a new published page) go to the decision register through the
`decision-inbox` skill.
