## 3. Divergences (findings, open)

Each finding is a difference between the code and the written specification. Choosing which side changes is an engineering decision, and none is made here. No safety code was changed.

### B2B-01 — A frame of an RX-checked ID with the wrong length is ignored, not treated as an RX fault (SWSR-402)

| | |
|---|---|
| Specification | SWSR-402: verify "checksum and length" of `0x260`, `0x1D2` (`0x262`, `0x1D3`) "and treat one failure as an RX fault". SWSR-406: on an RX fault, clear authority in the same call. Record T4 |
| C | A frame whose DLC differs from the RX-check entry does not match the entry, so it is handled like an unchecked ID. It is not validated and does not clear authority. Its signals and time stamp are not used. Applies to all six RX messages, both builds |
| Example | D08, every message: authority stays granted after a DLC 7 frame. Random: DLC 0, 6 and 7 on `0x1D2`, `0x226`, `0x260`, `0x262`, `0xAA` (both builds) |
| Effect | Reaction is delayed, not a wrong grant. If only wrong-length frames arrive, the RX timeout clears authority after 5 periods plus at most one 10 ms task period. A brake press carried in a wrong-length `0x226` frame is not acted on until the next valid `0x226` frame (D14 with the deviation on: cleared on the next nominal `0x226` frame, 25 ms later) or the timeout |
| Realistic path | Needs a frame on the car bus with an RX-set ID and a DLC other than 8. A healthy bus does not produce it. A faulty ECU, a wiring fault or an attacker on the bus could (ISO/SAE 21434 relevance). Rate of occurrence: not established |
| Options | (a) Amend SWSR-402: a length mismatch makes the frame invalid and ignored, covered by the SWSR-401 timeout. (b) Change the code so that a length mismatch on an RX-set ID is an RX fault (CT-1 change record) |
| Decision | 2026-10-13, project maintainer, on the recommendation: (b) change the code, reference build. Proposed as WP-W-03 ATC-25 with a [change proposal](../../../07-supporting/impact/change-2026-10-13-opendbc-rx-length-fault.md). Not implemented; the finding stays open until the code changes |
| Also answers | WP-W-05 OI-1 (brake edge when the brake frame fails validation): for `0x226` the only possible validation failure is length (no checksum). The C does not process the brake in that frame. Revocation follows from the next valid `0x226` with the brake pressed. Draft observation from this run, not a review result |

### B2B-02 — "Moving" is the sum of the wheel speeds, not "any wheel speed non-zero" (SWSR-302)

| | |
|---|---|
| Specification | SWSR-302: clear authority when BRAKE_PRESSED rises, "or is set while any wheel speed is non-zero". Record T3 |
| C | Standstill is decided on the sum of the four decoded wheel speeds, so non-zero speeds of opposite sign that sum to zero count as standing |
| Example | D06: brake held, then a `0xAA` frame with FR = +0.01 km/h, FL = −0.01 km/h. The model clears; the C keeps authority. Random: the same class in both builds |
| Effect | Only for wheel speeds of mixed sign summing exactly to zero. A brake rising edge still clears in every case; only the "held while moving" path is affected |
| Realistic path | Requires negative wheel-speed values in `0xAA`. Whether the reference Corolla reports signed wheel speeds (for example in reverse) is not established; with non-negative speeds the two readings are equivalent |
| Options | (a) Amend SWSR-302 to the sum or mean of the wheel speeds. (b) Change the code to test each wheel |
| Decision | 2026-10-13, project maintainer: left open until a reference-car log shows whether `0xAA` carries negative wheel speeds. The `0xAA` layout is now recorded in WP-S-05 S-06 (provisional, LC-01) |

### B2B-03 — Cruise becoming active while main is off is refused at once; the specification only knows the 150 ms rule (SWSR-405(c), record T10c)

| | |
|---|---|
| Specification | SWSR-405(c): flag an RX fault on CRUISE_ACTIVE = 1 with MAIN_ON = 0 "for longer than its tolerance time". Record T10c: "CRUISE_ACTIVE while MAIN_ON is off for > 150 ms" |
| C | Reference build: when the mismatch is first seen on a `0x1D2` frame, which means cruise became or is active while main is already off, authority is cleared in the same call. A mismatch that starts on `0x1D3` (main switched off while cruising) is cleared after > 150 ms as specified |
| Example | D12: main off, cruise rising edge. The model grants (clear only after 150 ms); the C grants and clears in the same call. Random: 72 of the 80 diverging reference sequences end on this cause (two signatures, 68 and 4) |
| Effect | The code is stricter than the specification (safe direction). The specification and the SM record are incomplete, and the generated WP-W-05 §5.2 table does not show the immediate refusal |
| Options | Add the immediate refusal to SWSR-405(c) and to the SM record (for example split T10c into an immediate refusal on `0x1D2` and the 150 ms rule), then regenerate WP-W-05 §5.2. No code change |
| Decision | 2026-10-13, project maintainer (on the recommendation): change the specification, not the code. Applied: WP-W-02 v0.16 SWSR-405(c), SM record T1/T8/T10c guards, WP-W-05 §5.2 regenerated, model updated. Re-run in §6. A maintainer decision, not an independent review |

### B2B-04 — T10b supervision starts at the first safety task after the grant, not at the grant (SWSR-408)

Found in run r3 (§8), on opendbc `273f44e`, the first pin that implements T10b.

| | |
|---|---|
| Specification | SWSR-408: "clear authority when no `0x2E4` frame has been accepted for > 50 ms" while authority is granted (`0x343`: > 100 ms). Acceptance: "Clear at 50/100 ms + task period". The text does not say when supervision starts; the model starts it at the grant (MA-08) |
| C | `tx_arrival_ok()` (`safety.h:421-440`) resets the arrival times at the first safety task that finds authority granted, and "granted before" is what the previous safety task left. A frame that stops at the grant is therefore cleared up to one task period (10 ms) later than 50 ms after the grant |
| Example | D13c: after the T11 revocation and a new cruise edge, `0x2E4` is not sent. The literal model clears at the 910 ms task (more than 50 ms after the grant); the C still grants authority at that task. With the deviation `arrival_from_first_tick` on, the model and the C agree on every event |
| Effect | The C clears within the acceptance "50/100 ms + task period", so no requirement is violated in time. The wording leaves the start of supervision open, so the model and the C read it differently |
| Options | (a) Clarify SWSR-408: supervision starts at the first safety task that finds authority granted (the code's reading). (b) Change the code to start at the grant. Recommendation: (a), no code change |
| Decision | Open: WP-W-02 OI-13 (a) |

### B2B-05 — "Accepted" frame: the C counts every whitelisted frame (SWSR-408), not compared

| | |
|---|---|
| Specification | SWSR-408 counts frames "accepted" |
| C | `tx_arrival_update()` (`safety.h:245-252`) runs for every whitelisted frame that reaches the TX hook (`safety.h:300`), before the content and rate checks. A frame refused for its content (torque, request bit) still counts as an arrival |
| Run | Not observable in this harness: the harness sends neutral frame content, so no frame is refused for content, and a frame refused by the rate check is followed by the T11 revocation after the third refusal. The deviation `arrival_counts_refused` written for this made no difference in any run and was removed (the gate rejects an option that is never needed) |
| Effect | A host that sends only refused `0x2E4` frames keeps authority in the C; under the wording it would lose it after 50 ms. The refused frames do not actuate |
| Decision | Open: WP-W-02 OI-13 (b) (wording "received" or a code change). Comparing it needs frame content in the model (README §3) |

### B2B-06 — Authority comes back after a safety-mode set without a new driver engagement (SWSR-301 against SWSR-311)

**Closed in r6 (§11):** SWSR-311 amended (DQ-080), code ATC-26 at the pin since opendbc `515b9a2`; D19a and D19b agree with no re-grant.

Carried over from the retired parallel harness (`assurance/models/b2b`, candidate BB-C-01, scenarios BB-08a/b), as decided by the maintainer on 2026-10-13. Reproduced here as D19a and D19b (§9); the C and the model agree, so this is a question about the specification, not a divergence.

| | |
|---|---|
| Specification | SWSR-311: a mode set resets all edge state. SWSR-301: authority is granted only on a driver engagement (a rising edge of CRUISE_ACTIVE). Record T7, MA-01 |
| C and model | After a mode set (T7) while CRUISE_ACTIVE stays 1, the reset makes the held 1 look like a rising edge. If every RX check has been received again before the next `0x1D2`, that frame grants authority (D19b: cleared at 450 ms, granted again at 454.5 ms). If one has not, the edge is consumed and authority stays off (D19a, D10) |
| Effect | A mode set while engaged (`0xdc` from the host, a heartbeat loss, a harness change) can be followed by authority again within one `0x1D2` period, without the driver re-engaging. Whether that meets SWSR-301 depends on whether a held CRUISE_ACTIVE after a reset counts as an engagement |
| Options | (a) Keep the behaviour and say in SWSR-311 / SWSR-301 that a held CRUISE_ACTIVE after a mode set is a new engagement. (b) Require a falling edge first after a mode set (code change in opendbc, reference build). Recommendation: (b), because a mode set while engaged follows a fault or a host request, and re-engagement should be the driver's |
| Decision | Open: WP-W-02 OI-14 |

## 5. Limits of this run

- **Independence.** The model was written by the author of the SM record and of the SWSR texts, after reading the C ([README §4](../README.md#4-independence-and-its-limits)). The run checks the code against the written specification. It does not validate the specification.
- **Host only.** This is a host build of the safety C (x86, gcc, `-O0`, `ALLOW_DEBUG`). It says nothing about the target binary, the 100 Hz task timing or panda code (T6, T10a).
- **Coverage.** This is coverage of SM-record transitions only. Code coverage of the C during these runs was not measured.
- **Configuration.** Only the reference configuration (Toyota, parameter 73) was driven.
- **Tools.** The model, harness, `CANPacker` and DBC are not classified in WP-P-07.
