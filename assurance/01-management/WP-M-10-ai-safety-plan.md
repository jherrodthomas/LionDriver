## 1. Purpose and scope

This plan implements sub-claim **G3** of the [assurance strategy](WP-M-01-assurance-strategy.md#32-top-level-claim): the ML components of LionDriver are adequately specified, evaluated and monitored, and their errors are handled as SOTIF functional insufficiencies inside a safety-monitored architecture. It applies ISO/PAS 8800 at the level of topics (no clause numbers are cited; check them against the licensed copy) and the ASPICE 4.0 machine-learning processes.

The central constraint: **every AI component in LionDriver was trained by comma.ai on data that LionDriver cannot access** ([WP-M-01 §2](WP-M-01-assurance-strategy.md#2-starting-point)). LionDriver does not train models. The plan therefore follows an "acquired, pre-trained model" route (§5) in which the training-side activities are replaced, as far as possible, by black-box characterization, architectural containment and field monitoring. What cannot be replaced is recorded as a limitation of the argument, not hidden.

## 5. The acquired, pre-trained model route

ISO/PAS 8800 assumes that the developer of the AI system controls its data and training. LionDriver does not. The route below is LionDriver's tailoring; it needs the assessor's confirmation (OI-1).

| PAS 8800 / MLE topic | Normal expectation | LionDriver substitute | Residual limitation |
|---|---|---|---|
| AI safety requirements (MLE.1) | Derived before training | Derived from the HARA, SOTIF hazards and ODD **after the fact**, in [WP-C-11](../02-concept/WP-C-11-ai-system-definition-and-safety-requirements.md); used as acceptance criteria for an existing model | Model was not designed against these requirements; failures can only be found, not prevented |
| Data management (SUP.11) | Training, validation and test data specified, collected, labelled, controlled | Applies only to **LionDriver evaluation data** (§6.3). Training data: recorded as unknown | No argument on training-data coverage, label quality, bias or ODD representativeness |
| AI architecture (MLE.2) | Designed by developer | Described as received: inputs, outputs, input preprocessing, recurrent state, runtime and fallbacks (from `modeld.py`, `parse_model_outputs.py`) | Internal architecture visible only through the ONNX graph (AI-1, AI-3); not at all for AI-2 |
| Training (MLE.3) | Controlled, reproducible | Not performed. Provenance recorded: LFS hash, upstream commit, commit message identifiers (e.g. `4bcf732` "7a933c1c-…/12864", `0e0c7c7` "ea1600cb/12864" — opaque comma-internal identifiers) | Not reproducible; cannot be audited |
| Model testing (MLE.4) | Tested against ML requirements on independent test data | Black-box testing of the pinned artefact against WP-C-11 requirements on LionDriver evaluation data, replay and simulation ([WP-W-10](../05-software/WP-W-10-ml-engineering.md)) | Test data independence from training data can be argued only by time and source (§6.3) |
| Safety analysis of the AI system | During development | Insufficiency analysis (WP-C-06) with AI error causes: distribution shift, rare scenarios, sensor degradation, recurrent-state errors, numerical faults | As above |
| Architectural measures | Chosen by developer | Containment by the safety envelope; driver supervision enforced by DM; runtime monitors added by LionDriver (§7) | The containment argument must close GAP-04 (limit rationale) to hold |
| Operation-phase monitoring | Developer's fleet data | LionDriver-owned field data only ([WP-O-04](../09-production-operation/WP-O-04-field-monitoring.md)) | Small fleet (initially one vehicle) |

### 6.3 LionDriver evaluation data

- **Source.** Drives of the reference Corolla by safety drivers under [WP-V-07](../06-validation/WP-V-07-vehicle-test-operations.md); recorded scenario tests; simulation output (labelled as such).
- **Independence from training data.** LionDriver cannot inspect comma's training set. Data recorded by LionDriver after the pinned model's release date cannot have been used to train that model. However, logs uploaded to comma's servers may enter *future* upstream models. Evaluation data used to judge a future model must therefore either not be uploaded to comma, or its upload history must be recorded so that independence can be judged.
- **Controls.** Dataset versioning by hash, ODD-attribute tagging (road type, weather, light, speed), label specification and review, storage under LionDriver control, privacy handling (camera and driver-camera data) aligned with [WP-M-09](WP-M-09-cybersecurity-plan.md).

## 7. Runtime monitoring (GAP-22)

Today there is no confidence or OOD gating of the control action, no model hash or signature check at load, and models are deserialized with `pickle` (`modeld.py:150, 159`, `helpers.py:15-20`). Candidate measures, decided in [WP-C-07](../02-concept/WP-C-07-sotif-functional-modifications.md) and specified in [WP-S-03](../03-system/WP-S-03-technical-safety-concept-architecture.md):

| # | Measure | Purpose |
|---|---|---|
| RM-1 | Verify artefact hash against the release manifest before deserialization | Integrity; prevents silent model substitution (also a CS control) |
| RM-2 | Non-finite and range checks on AI-1 outputs, with handover rather than silent clamping | Numerical faults; complements `controlsd.py:140-147` |
| RM-3 | Uncertainty / plausibility monitor on the action using model standard deviations and consistency with the planned path | Detect likely triggering conditions; trigger alert and handover |
| RM-4 | DM validity derived from model uncertainty and input quality instead of a constant `True` | Make DM degradation visible to `dmonitoringd` and `selfdrived` |
| RM-5 | Inference timing monitor with a defined reaction | Bound stale-model actuation (relates to GAP-16) |

Each measure needs its own false-positive / false-negative evaluation in WP-W-10.

## 8. Operation-phase monitoring

[WP-O-04](../09-production-operation/WP-O-04-field-monitoring.md) collects, for LionDriver-operated vehicles: takeovers and disengagements with context, FCW events, envelope limit hits (safety replay), DM alert levels and fallbacks, runtime-monitor triggers (RM-1…RM-5), model frame drops. Findings enter [WP-P-03](../07-supporting/WP-P-03-problem-resolution.md); new triggering conditions update WP-C-06 and may restrict the ODD.

## 9. Model change control (D-05)

1. Model artefacts are pinned per release by LFS hash, together with the tinygrad commit used to compile or run them ([WP-P-01](../07-supporting/WP-P-01-configuration-management-plan.md)).
2. Any change to `openpilot/selfdrive/modeld/models/*`, the `tinygrad_repo` pin, `modeld.py`, `dmonitoringmodeld.py`, `parse_model_outputs.py`, `fill_model_msg.py` or `modeld/SConscript` is a SOTIF-relevant change request ([WP-P-02](../07-supporting/WP-P-02-change-management.md)).
3. The change request carries an impact analysis using the template in [WP-M-12 §7](WP-M-12-impact-analysis.md), plus: provenance record, model replay comparison with the previous pin, re-run of WP-W-10 model tests and the WP-V-03 known-scenario suite, and an update of WP-C-06.
4. Upstream "bump" commits are inspected at diff level: `d05c2d9` ("bump tinygrad") also reverted `a0d47bc` and rebuilt the big models.
5. A model change that cannot complete step 3 is not released. Upstream model updates are not taken automatically (D-02).
